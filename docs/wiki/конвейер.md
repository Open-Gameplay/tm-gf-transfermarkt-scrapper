# Конвейер

## Что это

Скрейпер v2 (ветка `scraper-v2`): дёргает локальный transfermarkt-api (:8000), качает фото с CDN и
собирает **канон-JSON на TM-id** ([[данные]], схема — вики GameplayFootball
[[данные-из-transfermarkt]]). Каждый запрос проходит через rate limiter и SQLite resume-кэш; краул
можно прерывать и продолжать, повторный прогон на TM не ходит.

## Архитектура (реализовано 2026-08-29)

```
config.py          API base, лимиты (HTML/CDN), Tier-1 список, пути
client.py          HTTP: curl_cffi (TLS-fingerprint Chrome) → fallback requests,
                   глобальный token-bucket (html/cdn отдельно), AIMD-семафор,
                   circuit breaker, ретраи с учётом Retry-After, resume-кэш (2xx + 4xx-блоки)
cache.py           SQLite resume-кэш: requests(url PK, status, payload, fetched_at)
fetch/
  competitions.py  /competitions/search/{name} → лиги Tier-1; /competitions/{id}/clubs
  clubs.py         /clubs/{id}/profile (colors, стадион, лига, лого)
  rosters.py       ★ /clubs/{id}/players (1 запрос на команду) + /national-teams/{id}/players
  profiles.py      /players/{id}/profile (точечно: outfitter, imageUrl, мульти-позиции)
  market_values.py /players/{id}/market_value; при 403 API — прямой fallback на ceapi TM
  coaches.py       /coaches/{id}/profile + прямой парсинг /mitarbeiter/ для coach_id
build_canon.py     сборка канон-JSON (чистая, идемпотентная, валидация по canon_schema.json)
download_images.py логотипы/эмблемы/фото с CDN (bucket cdn, отдельный лимит)
canon_schema.json  JSON Schema канона
crawl.py           оркестратор: crawl.py --scope {pilot,tier1} [--spot N] [--images]
probe.py           probe.py --html | --cdn — замер лимитов (см. «Лимиты»)
tests/             pytest: token-bucket, AIMD, circuit breaker, resume-кэш,
                   интеграция request() против mock-HTTP-сервера (30 тестов)
```

Порядок сбора: competitions → clubs → rosters (основной источник составов) → точечно
profiles/market_values → coaches (+ `/mitarbeiter/` для coach_id). Выход канона — `data/canon/`.

Параллелизм — **AIMD**: `client.py` держит `AdaptiveSemaphore` (старт `TM_CONCURRENCY`, рост до
×2 после успехов, деление пополам при 429/5xx/ошибке соединения). Token-bucket всё равно режет
глобальную частоту — AIMD лишь регулирует число запросов в полёте, безопасно при любых лимитах.

## Адаптивная скорость (AIMD на rps) и память ограничений

Помимо фиксированного `TM_HTML_RPS` скорость **самонастраивается**: на троттлинг (429/5xx/блок-
страница/разрыв соединения) `RateAimer` делит rps пополам (пол — `TM_HTML_RPS_MIN`, дефолт 1.0),
после 50 успехов плавно растёт на 25% (до `TM_HTML_RPS`). Параллельно срабатывает circuit breaker
и AIMD-конкурентность — все три механизма консервативные и не конфликтуют.

**Память ограничений**: текущие скорости сохраняются в `data/rates.json` (`TM_RATES_PATH`) при
каждом изменении. Следующая сессия стартует с сохранённой скорости (`min(saved, configured)`), а
не слепо с 8 rps — если прошлый краул закончился троттлингом на 4 rps, новая сессия начнёт с 4 и
плавно вернётся к 8, не сжигая ошибки. «Запоминание» отключается: `TM_RATES_PATH=""` или
`Client(adaptive_rate=False)` (probe так и делает — мерит фиксированный уровень).

Пример динамики при «потолок стал ниже»: 8 → троттл → 4 → троттл → 2 → 1 (пол) → успехи → 1.25 →
… → снова к 8, если TM отпустил.

## Лимиты (эксперимент 2026-08-29, probe.py)

Проверено сериями с плавным наращиванием, критерий — отсутствие 429/403/5xx и блок-страниц.
**429/Retry-After за эксперимент не наблюдались** (в коде ретраев учтён на случай появления).

| Бакет | Потолок (чисто) | Безопасно | Примечание |
|---|---|---|---|
| HTML (через API) | 3.0 rps burst; **прямой замер TM: чисто даже на 75 rps** (потолок выше) | **8.0 rps** | 9× запас до наблюдаемого потолка; каждый вызов API = 1 живой запрос к TM |
| CDN (img.a.transfermarkt.technology) | 20 rps clean (40 запр.) | **15 rps** | **не ограничен** как HTML — картинки можно качать быстро |

Дефолты — в `config.py`, переопределяются env (`TM_HTML_RPS`, `TM_CDN_RPS`).

**Прямой замер потолка TM (2026-08-29):** `probe.py --html-direct` гонял напрямую по
www.transfermarkt.com (в обход API) на 5→10→20→40→60→75 rps — **всё чисто (10/10 × 200 на каждом
уровне)**. Потолок выше 75 rps. Вывод: внешние «блоки на ~75 rps» были почти наверняка
**переполнением самого API** (клиент слал 75 rps в API, тредпул ~40 потоков не успевал → таймауты/
ошибки), а не баном TM. Отсюда и безопасные 8.0 rps (5× быстрее прежних 1.5) — всё ещё с 9-кратным
запасом до наблюдаемого потолка. Продолжительный (часовой) краул на 75 rps не тестировался — на
него не претендуем.

**Встроенный рейтлимитер API**: в transfermarkt-api slowapi с дефолтом `2/3seconds`
(`app/settings.py: RATE_LIMITING_FREQUENCY="2/3seconds"`, `RATE_LIMITING_ENABLE=false` — локально
**выключен**). Если API поднять с включённым лимитом (env/`.env`), он сам будет резать до ~0.67 rps
и отдавать 429 с `Retry-After` — тогда узким местом станет API, а не TM. Клиент это переживает
корректно: уважает `Retry-After`, 429 не кэшируется (см. «Resume-кэш»), но эффективная частота
упадёт. Перед полным краулом проверь, что API поднят с `RATE_LIMITING_ENABLE=false`.

**Узкое место самого API ~40 rps**: синхронные эндпоинты исполняются в тредпуле anyio (40 потоков,
захардкожено в anyio 4.7). Устойчивая частота API ≈ `40 / t_avg` (для быстрых страниц ~0.2 с ≈ 200
rps, для тяжёлых ~1 с ≈ 40 rps). Клиент на 8 rps API переваривает без проблем. Если когда-нибудь
понадобится >40 rps через API — нужно поднимать тредпул/воркеры API, иначе запросы встанут в очередь.

## Веса запросов (динамическая скорость)

Лимит TM **глобальный на IP**, не per-endpoint — делить его на отдельные бакеты по эндпоинтам
незачем. Что реально различается — **стоимость** вызова: `/players/{id}/market_value` = **2 TM
запроса** (страница + ceapi-график). Поэтому `client.request(weight=2)` для него: token-bucket
съедает 2 токена, эндпоинт сам замедляется вдвое внутри общего бюджета. Остальные эндпоинты —
weight=1. Параллелизм при этом динамический (AIMD), см. выше.

Ловушка бюджета: `/players/{id}/market_value` = **2 запроса к TM** (страница + ceapi-график).
Если качать историю стоимости массово — учитывать фактор ×2 (или качать на половинной частоте).

## Известные ограничения / находки

- **API не даёт market_value**: TM 403-ит транспорт API (голый `requests`, статичный UA Chrome 113)
  на `/marktwertverlauf/` и `ceapi/marketValueDevelopment/graph/`. Наш curl_cffi (Chrome 131) их
  пробивает — в `fetch/market_values.py` сделан прямой fallback на ceapi (обосновано, как
  `/mitarbeiter/`). Если починено в API — fallback останется запасным.
- **Per-page 403**: отдельные страницы игроков TM отдаёт 403 даже curl_cffi (0 байт) — похоже на
  honeypot/флаг. Такие записи пропускаются и кэшируются (403), пилот пережил их без последствий.
- `national_teams.flag` — API флаг не отдаёт (только эмблема); в каноне null.
- `players.weight` — в TM нет, эвристика в конвертере (не поле канона).
- `competitions.logo` — из лиг Tier-1 не достаётся, null.

## Resume-кэш и идемпотентность

`cache.py` — `requests(url PRIMARY KEY, status, payload, fetched_at)`, WAL, TTL 7 дней. Кэшируются
**персистентные** исходы: 2xx (resume) и 4xx-блоки (403-хонейпоты, 404); транзиентные **429** и
**5xx не кэшируются** (это «повтори позже» — замораживать их в кэше нельзя). Поэтому повторный
прогон не долбит TM даже по заблокированным URL, но при этом не запоминает временные троттлинги.
Проверено: второй `crawl.py --scope pilot` — 0.6 с, ноль сетевых запросов, канон тот же.
`build_canon.py` не мутирует кэш и вход — читает записи и пишет `data/canon/` заново.

## Тесты

`pytest` — 30 тестов: математика token-bucket, AIMD-семафор, circuit breaker, resume-кэш и
интеграция `client.request()` против локального mock-HTTP-сервера (ретраи 429/503, respect
`Retry-After`, кэш-хиты, кэширование 403, ротация UA). Запуск: `.venv\Scripts\python -m pytest`.
Тесты не ходят в сеть — только в mock-сервер. Перенесены из `transfermarkt_scrapper_upgraded`
(ветка fix) и адаптированы под API scraper-v2.
