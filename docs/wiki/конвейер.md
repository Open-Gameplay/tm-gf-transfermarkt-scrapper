# Конвейер

## Что это

Скрейпер v2 (ветка `scraper-v2`): дёргает локальный transfermarkt-api (:8001), качает фото с CDN и
собирает **канон-JSON на TM-id** ([[данные]], схема — вики GameplayFootball
[[данные-из-transfermarkt]]). Каждый запрос проходит через rate limiter и SQLite resume-кэш; краул
можно прерывать и продолжать, повторный прогон на TM не ходит.

**Статус (2026-09-01):** Полный краул завершён. Все лиги TM (94), все сборные (246), все клубы
(1598) и игроки (44,933) скачаны. Исправлены 3 бага API.

## Архитектура (обновлено 2026-09-01)

```
config.py          API base (:8001), лимиты (HTML/CDN), пути
client.py          HTTP: curl_cffi (TLS-fingerprint Chrome) → fallback requests,
                   глобальный token-bucket (html/cdn отдельно), AIMD-семафор,
                   circuit breaker, ретраи с учётом Retry-After, resume-кэш (только 2xx)
                   api() — bypass circuit breaker для локального API
cache.py           SQLite resume-кэш: requests(url PK, status, payload, fetched_at)

fetch_leagues.py   TM index (/wettbewerbe/national/) → все лиги TM (94)
fetch_club_profiles.py  /clubs/{id}/profile (colors, стадион, лига, лого)
fetch_club_rosters.py   /clubs/{id}/players (составы)
fetch_national_teams.py /national-teams/most-valuable (все 246) + profile + roster
topup.py           докачка data/full/clubs.json до скачиваемых лиг (см. [[данные]]):
                   profile+roster для клубов из data/clubs.json, отсутствующих в файле,
                   затем картинки (лого/флаги/лица) через CDN; --images-only — догон картинок

download_pilot_images.py  faces, logos, emblems, flags с CDN
build_pilot_json.py       сборка JSON: data/full/clubs.json + national_teams.json
retry_failures.py         повтор всех ошибок
pilot_crawl.py            оркестратор: все шаги + retry
session_viewer.py         веб-дашборд: http://127.0.0.1:8080

tests/             pytest: token-bucket, AIMD, circuit breaker, resume-кэш,
                   интеграция request() против mock-HTTP-сервера (51 тест)
```

Порядок сбора: competitions → clubs → rosters (основной источник составов) → club_profiles
(все клубы) → нац. сборные (most-valuable + profiles + rosters) → точечно player_extras
(stats/injuries/achievements через API) → coaches (+ `/mitarbeiter/` для coach_id).
Выход канона — `data/canon/`; конвертер в GF SQLite — `build_gf_database.py`.

Параллелизм — **AIMD**: `client.py` держит `AdaptiveSemaphore` (старт `TM_CONCURRENCY`, рост до
×2 после успехов, деление пополам при 429/5xx/ошибке соединения). Token-bucket всё равно режет
глобальную частоту — AIMD лишь регулирует число запросов в полёте, безопасно при любых лимитах.

## Адаптивная скорость (AIMD на rps) и память ограничений

Помимо фиксированного `TM_HTML_RPS` скорость **самонастраивается**: на троттлинг (429/5xx/блок-
страница/разрыв соединения) и на **серию из `TM_BLOCK_STREAK` (5) подряд 403** `RateAimer` делит rps
пополам (пол — `TM_HTML_RPS_MIN`, дефолт 0.5), после 50 успехов плавно растёт на 25% (до
`TM_HTML_RPS`). Параллельно срабатывает circuit breaker и AIMD-конкурентность — все три механизма
консервативные и не конфликтуют.

**Память ограничений**: текущие скорости сохраняются в `data/rates.json` (`TM_RATES_PATH`) при
каждом изменении. Следующая сессия стартует с сохранённой скорости (`min(saved, configured)`), а
не слепо с максимума — если прошлый краул закончился троттлингом, новая сессия начнёт с выученной
и плавно вернётся к максимуму, не сжигая ошибки. «Запоминание» отключается: `TM_RATES_PATH=""` или
`Client(adaptive_rate=False)` (probe так и делает — мерит фиксированный уровень).

Пример динамики при «TM прижал страницы игроков»: 2 → серия 403 → 1 → серия 403 → 0.5 (пол) →
окно сбросилось → успехи → 0.625 → … → снова к 2, если TM отпустил.

## Лимиты (эксперимент 2026-08-29, probe.py)

Проверено сериями с плавным наращиванием, критерий — отсутствие 429/403/5xx и блок-страниц.
**429/Retry-After за эксперимент не наблюдались** (в коде ретраев учтён на случай появления).

| Бакет | Что выяснили | Безопасно | Примечание |
|---|---|---|---|
| HTML (через API) | короткие серии чисто даже на 75 rps (главная страница), **но страницы игроков `/profil/spieler/` и `/marktwertverlauf/` блокируются по объёму уже после ~15-24 подряд на 8 rps** | **2.0 rps** | устойчивая скорость для чувствительных страниц; каждая вызов API = 1 живой запрос к TM |
| CDN (img.a.transfermarkt.technology) | 20 rps clean (40 запр.) | **15 rps** | **не ограничен** как HTML — картинки можно качать быстро |

Дефолты — в `config.py`, переопределяются env (`TM_HTML_RPS`, `TM_CDN_RPS`).

**Прямой замер потолка TM (2026-08-29):** `probe.py --html-direct` гонял напрямую по
www.transfermarkt.com (в обход API) на 5→10→20→40→60→75 rps — **всё чисто (10/10 × 200 на каждом
уровне)** для главной страницы. Это были короткие серии с паузами — они не показали реального
потолка. Проверка на чувствительных страницах (составы → профили/стоимости) выявила главное:
**TM блокирует `/profil/spieler/` и `/marktwertverlauf/` по объёму** — ~15-24 подряд запроса на 8 rps
проходят, дальше новые URL отдают 403 (0 байт) и остаются заблокированными для этих страниц
(проверено: те же URL 403 даже curl_cffi напрямую, а ранее успешные страницы продолжают отдаваться).
Поэтому устойчивый HTML-режим — **~1-2 rps**, а не 8. Высокие скорости годятся только для коротких
фаз (составы) и для CDN.

**Встроенный рейтлимитер API**: в transfermarkt-api slowapi с дефолтом `2/3seconds`
(`app/settings.py: RATE_LIMITING_FREQUENCY="2/3seconds"`, `RATE_LIMITING_ENABLE=false` — локально
**выключен**). Если API поднять с включённым лимитом (env/`.env`), он сам будет резать до ~0.67 rps
и отдавать 429 с `Retry-After` — тогда узким местом станет API, а не TM. Клиент это переживает
корректно: уважает `Retry-After`, но эффективная частота упадёт. Перед полным краулом проверь, что
API поднят с `RATE_LIMITING_ENABLE=false`.

**Узкое место самого API ~40 rps**: синхронные эндпоинты исполняются в тредпуле anyio (40 потоков,
захардкожено в anyio 4.7). Устойчивая частота API ≈ `40 / t_avg` (для быстрых страниц ~0.2 с ≈ 200
rps, для тяжёлых ~1 с ≈ 40 rps). Клиент на 2 rps API переваривает без проблем. Если когда-нибудь
понадобится >40 rps через API — нужно поднимать тредпул/воркеры API, иначе запросы встанут в очередь.

## Веса запросов (динамическая скорость)

Лимит TM **глобальный на IP**, не per-endpoint — делить его на отдельные бакеты по эндпоинтам
незачем. Что реально различается — **стоимость** вызова: `/players/{id}/market_value` = **2 TM
запроса** (страница + ceapi-график). Поэтому `client.request(weight=2)` для него: token-bucket
съедает 2 токена, эндпоинт сам замедляется вдвое внутри общего бюджета. Остальные эндпоинты —
weight=1. Параллелизм при этом динамический (AIMD), см. выше.

Ловушка бюджета: `/players/{id}/market_value` = **2 запроса к TM** (страница + ceapi-график).
Если качать историю стоимости массово — учитывать фактор ×2 (или качать на половинной частоте).

## Известные ограничения / находки

- **API не даёт market_value**: TM 403-ит транспорт API (голый `requests`, статичный UA Chrome 113)
  на `/marktwertverlauf/` и `ceapi/marketValueDevelopment/graph/`. Наш curl_cffi (Chrome 131) их
  пробивает — в `fetch/market_values.py` сделан прямой fallback на ceapi (обосновано, как
  `/mitarbeiter/`). Если починено в API — fallback останется запасным.
- **Per-page 403**: отдельные страницы игроков TM отдаёт 403 даже curl_cffi (0 байт) — похоже на
  honeypot/флаг. Такие записи пропускаются и кэшируются (403), пилот пережил их без последствий.
- `national_teams.flag` — API флаг не отдаёт (только эмблема); в каноне null.
- `players.weight` — в TM нет, эвристика в конвертере (не поле канона).
- `competitions.logo` — из лиг Tier-1 не достаётся, null.

## Resume-кэш и идемпотентность

`cache.py` — `requests(url PRIMARY KEY, status, payload, fetched_at)`, WAL, TTL 7 дней. Кэшируются
**только 2xx** (resume). 403/404-блоки и транзиентные 429/5xx **не кэшируются**: блок может пройти,
и retry-очередь (а также повторный запуск) дотянет их вместо пропуска. Поэтому повторный прогон не
ходит на TM по уже успешным URL, но при этом не «забывает» про неудавшиеся.
`build_canon.py` не мутирует кэш и вход — читает записи и пишет `data/canon/` заново.

## Retry-очередь (не пропускать игроков без данных)

Профили и истории стоимости (`fetch/profiles.py`, `fetch/market_values.py`) качаются **раундами**:
неудавшиеся игроки уходят в pending и повторяются после паузы
(`TM_FETCH_RETRY_ROUNDS`=5, `TM_FETCH_RETRY_COOLDOWN`=60 с). Если TM блокировал страницы в момент
запроса — через паузу (и после сброса окна) те же URL ретраятся, а не пропускаются. Только если
игрок так и не отдался за все раунды, он остаётся без spot-данных (но с данными состава) — и будет
дотянут следующим запуском, потому что провалы не кэшируются. В сочетании с circuit breaker и
адаптивной скоростью (см. «Адаптивная скорость») это даёт «лучше подождать, чем оставить без
данных».
